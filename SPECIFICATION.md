Это итоговая спецификация бэкенд-архитектуры для ваших Go-сервисов. Она адаптирована под нужды агентства: высокая скорость разработки, предсказуемость для разработчиков и идеальная совместимость с AI-агентами (Cursor/Windsurf).

# Go Backend Architecture Specification (Modular Slice Design)
**Версия:** 1.0 | **Статус:** Архитектурный стандарт агентства
* * *

## 0. Быстрый старт: Структура проекта
Архитектура построена по принципу **Vertical Slices (Вертикальные срезы)**, организованных вокруг API-ресурсов. Это "FSD для бэкенда".

**Основная идея:** Спецификация (Bruno) является единственным источником правды. Код структурирован так, чтобы папки в проекте на 100% совпадали с группами эндпоинтов в контракте.

### Структура проекта
```text
internal/
├── modules/           Бизнес-логика, разделенная на ресурсные модули (слайсы)
│   └── [resource]/    Пример: orders, users, billing
│       ├── delivery/  HTTP Handlers, парсинг DTO, валидация запросов
│       ├── service/   Бизнес-логика, оркестрация, транзакции
│       ├── repository/Работа с БД (SQL-запросы для этого модуля)
│       ├── dto.go     Структуры запросов/ответов (1:1 с контрактом)
│       └── module.go  Инициализация модуля и регистрация роутов
├── shared/            Инфраструктурный слой (Shared Kernel)
│   ├── database/      Коннект к БД, миграции
│   ├── middleware/    Auth, Logging, Recovery
│   ├── response/      Единый формат ответов (Success/Error)
│   └── logger/        Настройка Zap/Slog
├── cmd/app/           Точка входа (DI Container, запуск сервера)
├── migrations/        SQL файлы миграций
└── docs/api/          API-контракты (Source of Truth)
```

* * *

## 1. Правила зависимостей (ВАЖНО!)
Импорты разрешены только **вниз** и в **Shared**. 
1.  **Modules → Shared:** Разрешено (использование БД, логгера, общих ошибок).
2.  **Shared → Modules:** ❌ ЗАПРЕЩЕНО. Shared должен быть чистым.
3.  **Module A → Module B:** ❌ ЗАПРЕЩЕНО напрямую. 
    *   *Как надо:* Если модулю `Orders` нужны данные из `Users`, он использует интерфейс `UserService`, который внедряется (DI) при старте.
4.  **Внутренняя иерархия модуля:** `delivery` → `service` → `repository`.

### Public API модуля
Единственной точкой входа в модуль является файл `module.go`. Другие модули не должны импортировать `repository` или `delivery` чужого модуля.

* * *

## 2. Слои модуля (Segments)

### 2.1 delivery (Вход)
Отвечает за протокол (HTTP). Здесь нет бизнес-логики.
- Парсинг JSON в структуры из `dto.go`.
- Вызов сервисного слоя.
- Отправка ответа через `shared/response`.

### 2.2 service (Мозг)
Чистая бизнес-логика.
- Не знает про HTTP или SQL.
- Работает с интерфейсами репозиториев.
- Управляет транзакциями.

### 2.3 repository (Данные)
- Прямые SQL-запросы.
- Не содержит бизнес-логики (только CRUD и фильтры).
- Каждый модуль работает только со своими таблицами.

* * *

## 3. Contract-First Workflow
Мы не пишем код, пока нет контракта в Bruno.

1.  **Define:** Описать эндпоинт в `bruno/`.
2.  **DTO:** Создать структуры в `internal/modules/[resource]/dto.go`, в точности повторяющие JSON.
3.  **Implement:** Написать Handler -> Service -> Repo.
4.  **Test:** Запустить Bruno-коллекцию против локального сервиса.

* * *

## 4. Обработка ошибок и ответов
Для обеспечения единообразия на фронтенде, все ответы бэкенда должны использовать `shared/response`.

**Успех (200 OK):**
```json
{
  "success": true,
  "data": { ... }
}
```

**Ошибка (4xx, 5xx):**
```json
{
  "success": false,
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "Описание для разработчика",
    "trace_id": "uuid"
  }
}
```

* * *

## 5. Инструкции для AI-агентов (Prompting)
При работе с этим проектом, следуй правилам:
1.  **Новый функционал:** Начинай с анализа `.bru` файлов в папке `bruno/`. Код должен соответствовать контракту.
2.  **Создание модуля:** Если добавляешь новый ресурс, создавай полную структуру в `internal/modules/[name]` с разделением на `delivery`, `service`, `repository`.
3.  **DRY vs Isolation:** Предпочитай изоляцию модулей. Если двум модулям нужна похожая логика — продублируй её или вынеси интерфейс. Не создавай жестких связей между ресурсами.
4.  **Naming:** Используй существительные во множественном числе для названий модулей (`orders`, `products`).

* * *

## 6. Тестирование
1.  **Unit-тесты:** Рядом с файлами `service.go` для проверки сложной логики (мокаем Repo).
2.  **Integration-тесты:** Проверка `repository` с реальной базой в Docker.
3.  **API-тесты:** Сценарное тестирование через Bruno или `go-resty` в папке `tests/`, проверяющее цепочку эндпоинтов.

* * *

## 7. Технологический стек
*   **Language:** Go 1.25+
*   **Router:** `chi/v5` (легковесность и стандартные middleware)
*   **Database:** PostgreSQL + `sqlx` или `pgx` (избегаем тяжелых ORM для прозрачности SQL)
*   **Logs:** `zap` (структурированный JSON)
*   **Config:** Environment variables (12-factor app)
*   **Contract:** Bruno (обязательно коммитим в репозиторий)
